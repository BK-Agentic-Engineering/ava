# LifeMate — Public Description

> Editorial note: This file reformats the organizer text supplied by the team. Wording, examples and requirements are retained; the formula is also transcribed from `image.png`. It has not been checked against a live official page. Examples containing `...` are illustrative, not executable JSON. The source included “Data Train + Public test: Download” without a URL.

Voice is becoming the main way people talk to machines. The next generation of devices - smart speakers, in-car assistants, smart TVs, earbuds, watches, home robots - will have small screens or none at all, yet they will connect to the same apps and services people already rely on. A parent tells the living-room speaker to cool the house before leaving the office; a driver asks the car to pay the electricity bill; an office worker tells their earbuds to book a ride home after a late meeting; a shop owner asks the kitchen speaker to order lunch for the staff; a grandparent who never learned to use apps asks the TV to set a reminder to take medicine. On a phone, each of these tasks takes many taps across several apps; on a screenless device, it is only possible if the assistant can act on its own — yet today’s voice assistants mostly answer questions rather than act. What people want is to simply say it in plain Vietnamese — “Tôi sắp về nhà, bật điều hòa phòng khách và đặt xe đón tôi”, “Chuyển cho mẹ 500 nghìn”, “Tắt hết đèn tầng một”, “Nhắc tôi họp lúc ba giờ chiều mai” — and have it done.

LifeMate challenges you to build an AI agent that turns spoken Vietnamese requests into actions: given an audio request, the user’s context and the apps and services connected to the device, the agent plans the steps, calls the right tools with the right arguments and leaves every app in the state the user asked for — or asks for the missing information when the request is incomplete, and takes no action when no installed app can handle it. The agent is judged on what it does, not what it says. The competition data is anchored in everyday Vietnamese digital life - smart home, banking, ride-hailing, food delivery, email - with requests spoken in synthetic and real voices from the North, Central and South regions, but the capability you build is general: voice-driven, multi-step tool use by an AI agent that can run on any device, from phones to smart speakers to cars.

## Task

### Input

- A spoken request: an audio file with the user’s latest request in Vietnamese, possibly mixed with common English words.

- User context: current time, timezone, location and a user profile (e.g. home and work addresses).

- Available apps: the apps connected to the device (smart home, banking, ride-hailing, food delivery, email, …), each exposing a set of tools described by a JSON schema.

- Conversation history: earlier turns of the same conversation, if any.

- A simulated environment holding the user’s app data (devices, accounts, reminders, contacts, …), which the agent can read and change only through tool calls.

### Output

The agent produces an ordered list of tool calls (tool name and arguments) to handle the user's request. Depending on the request and the information available, the agent may:

- Execute actions: Call the necessary tools in sequence to complete the task and achieve the expected final app state.

- Request missing information: Call sys.ask_missing_info to specify the intended tool and missing parameters when additional information is needed. This may happen after other tool calls have already been executed.

- Handle out-of-scope requests: Return an empty list of tool calls ([]) if none of the available apps can handle the request.

- Final state hash: Along with the tool calls, the agent submits a state_hash generated by the execution environment (env.get_state_hash()), which is used to verify the final app state.

### Example

- Input: audio “Tôi sắp về nhà, bật điều hòa phòng khách 26 độ và đặt xe đón tôi.”; context: the user is at work (227 Nguyễn Văn Cừ, Quận 5, TP.HCM), and user_profile.home is 123 Trần Hưng Đạo, Quận 5, TP.HCM; installed apps: smart_home, ride, banking, email.

- Output: the agent first reads the device list to find the living-room AC, then sets it and books the ride. The submission line for this sample (one JSON object per line in submission.jsonl) is:

```json
{"id": "s_000123", "tool_calls": [{"name": "smart_home.get_status", "arguments": {}},
  {"name": "smart_home.climate_set", "arguments": {"device_id": "ac_living_room", "mode": "cool", "temperature": 26}},
  {"name": "ride.book", "arguments": {"from": "227 Nguyễn Văn Cừ, Quận 5, TP.HCM", "to": "123 Trần Hưng Đạo, Quận 5, TP.HCM"}}],
 "state_hash": "9f2c4e7a1b8d3f60"}
```

## Evaluation

Each sample is scored on two things: whether the agent leaves the app data in the correct final state, and how closely its tool calls match the reference (gold) calls.

### Metrics

- State match: the submitted state_hash must equal the gold state_hash, otherwise the sample scores 0. Free-text (fuzzy) fields do not affect the hash. The state_hash must be computed by the zaic_tools environment (env.get_state_hash()) and can be reproduced by the organisers, who replay the submitted tool_calls in order with the matching version of zaic_tools; if the results differ, the organisers' result is final.

- Tool-call match: a submitted call matches a gold call when the tool name is the same, every non-fuzzy argument is identical, and every fuzzy argument has token-F1 > 0.6 (after lowercasing and Unicode NFC). Each call can match at most one call; order is not considered.

- Out-of-scope samples: if the gold list is empty, the sample scores 1 only when the submitted list is also empty.

- Missing information: sys.ask_missing_info is scored like any other tool;

### Scoring formula

If the gold list is empty, the sample scores 1 only when the submitted list is also empty; otherwise it scores 0.

Otherwise (the gold list is not empty):

```text
For non-empty gold calls:
P = M / (M + U)
R = M / |G|
Score_i = 0                              if hash_sys != hash_gold or M = 0
Score_i = 2 * P * R / (P + R)            otherwise

Final score = (100 / N) * sum(Score_i, i = 1..N)
```

## Data

The data has three splits with the same layout: train (about 1,600 with labels), public_test (about 600 samples, for the public leaderboard) and private_test (about 600 samples, released after the final Docker solution is frozen).

### Folder structure

```text
<split>/                                  # train | public_test | private_test
├── audio/<id>/<id>.wav                   # spoken request of each sample
├── <split>.jsonl                         # one sample per line
├── <split>_tools_catalog.json            # schema of every app tool
├── <split>_environment/<id>/state.json   # initial app data of each sample
├── sample_submission.jsonl               # public_test only
└── zaic_tools/                           # execution environment library for this split
```

### Files

- (1) Audio: the user’s latest request and every earlier user turn in history, in Vietnamese with some common English words (e.g. "book", "AC"). WAV, 16 kHz, mono, 16-bit; about 100% recorded by real speakers of different ages, genders and regions (North, Central, South).

- (2) `<split>.jsonl`: the input of each sample — id, audio path, user context (current_time, timezone, current location, user_profile, installed_apps) and earlier conversation turns (history). Train samples also include audio_text (the transcript of every user turn) and the label: the gold tool_calls, their tool_results and the final_state (the full data of every app the gold calls changed).

- (3) `<split>_tools_catalog.json`: the apps of the split and the schema of every tool — name (app.tool), description, kind (read, write, or meta for sys.ask_missing_info), parameters as JSON Schema and a short summary of the returned fields.

  - Parameters may carry x-ref (must be a valid ID in the app data), x-match: "fuzzy" (free text, scored by token-F1) and x-one-of (at least one of the listed groups is required, e.g. contact_id or phone_number). The catalog covers the whole split; the tools a sample may call are those of its context.installed_apps.

- (4) state.json: the initial app data of a sample (devices, accounts, contacts, reminders, …), with the actions of history already applied, plus a _meta block (question_id, current_time, tools). It is loaded by the environment; the agent must not read it directly.

### Execution environment

The organisers provide the zaic_tools Python library, which simulates the apps locally. Each sample runs in its own ToolEnv, which must be created only once. The environment checks each call against the tool schema, executes it, updates the app data and returns the result, which the agent can use in its next step. A call fails with "ok": false and an error message, typically when the tool does not exist or an argument has the wrong data type. Only tools from the apps listed in context.installed_apps (plus sys.ask_missing_info) may be called. Every call, successful or not, is logged; this call log, together with the final state hash, forms the submission. Each split comes with its own version of zaic_tools.

```python
import sys
sys.path.insert(0, "public_test")              # zaic_tools of the split
from zaic_tools import ToolEnv
# Create one environment per sample; root is the folder that holds the split folders
env = ToolEnv("public_test", "public_0001", root=".")
# Check arguments against the tool schema (nothing is executed)
env.validate("smart_home.light_set", {"power": "off"})
# -> {"ok": false, "error": "thiếu tham số bắt buộc: device_id"}
# Execute a call
# -> {"ok": true, ...} or {"ok": false, "error": "..."}
env.call("smart_home.get_status", {})
# Call log and final state hash for submission
env.get_tool_calls(), env.get_state_hash()
```

Rule: The agent/solution must not read, copy or parse any file under `<split>_environment/` (including state.json); all app data is accessed only through the organisers' zaic_tools, with exactly one ToolEnv per sample, and every call made on it must appear in the submission.

### Inference and submission template

The template below runs the agent on every sample of a split and writes submission.jsonl: one line per sample with id, tool_calls and state_hash. Run it from the folder that holds public_test/. Create exactly one ToolEnv per sample inside infer().

```python
import json
import sys
from pathlib import Path
ROOT = Path(".")                                  # folder that holds public_test/
SPLIT = "public_test"
sys.path.insert(0, str(ROOT / SPLIT))             # zaic_tools of the split
from zaic_tools import ToolEnv
def infer(item):
    env = ToolEnv(SPLIT, item["id"], root=ROOT)   # one environment per sample
    # Your pipeline: ASR (ROOT / SPLIT / item["audio"]) -> LLM -> env.call(tool, arguments) -> LLM -> ...
    # e.g. env.call("smart_home.get_status", {})
    #      env.call("smart_home.light_set", {"device_id": "light_kitchen", "power": "off"})
    return env.get_tool_calls(), env.get_state_hash()
with open(ROOT / SPLIT / f"{SPLIT}.jsonl", encoding="utf-8") as fin, \
     open("submission.jsonl", "w", encoding="utf-8") as fout:
    for line in fin:
        item = json.loads(line)
        tool_calls, state_hash = infer(item)
        fout.write(json.dumps({"id": item["id"], "tool_calls": tool_calls, "state_hash": state_hash}, ensure_ascii=False) + "\n")
```

### Submission file format

The file must be UTF-8 JSON Lines with exactly one line per sample in the split; see sample_submission.jsonl for the format.

## Rules

### Competition rounds

The competition runs on a leaderboard with two rounds:

- Round 1 — Public Test: teams develop their solutions, run them on public_test and submit the results. Scores appear on the public leaderboard and are for reference only during development.

- Final solution submission: the final solution is submitted as a Docker image, following the organisers’ separate guidelines. For scoring, the organisers mount the private test folder (same structure as public_test) into the container at /data, run the inference script and collect the result at result/submission.jsonl. The container must run fully offline, with no network access.

- Round 2 — Private Test: after teams submit and freeze their solutions, the organisers release private_test and its environment. Teams run their frozen solution with the provided zaic_tools and submit the results. The organisers re-run the submitted Docker image to verify the results, and the final ranking is based on the private_test score.

### Technical requirements

Every solution must meet all of the following requirements:

- Model size: the whole system (ASR, LLM and any other components) must have fewer than 6B parameters in total. The LLM must have fewer than 5B parameters and a context length of at most 16K (16,384) tokens.

- Data access: the agent must not read state.json directly; all reads and writes go through the execution environment.

- Allowed data and resources: teams may use public data and open-source models released before 26 October 2026, provided their licences allow it. Synthetic data may be generated with other services or models (LLM, TTS, …) during development, but these must not be used at inference. Labelling public_test or private_test (manually or with external services or models) to train or tune a solution is not allowed.

- Runtime and hardware: each sample must be processed within 30 seconds; samples that time out or fail to execute score 0. The solution must run fully offline, with no external APIs or services at inference. Scoring hardware: 1 NVIDIA A30 GPU, a 16-core Intel Xeon Gold 6442Y CPU and 64 GB RAM.

- Reproducibility: fix all random seeds (Python, NumPy, PyTorch, …) and use deterministic decoding for ASR and LLM, such as greedy decoding or temperature = 0. If a re-run differs from the submitted results, the organisers run the Docker image 5 times and use the average score as the official score.

- The solution / agent must not read, copy or parse any file under `<split>_environment/` (including state.json); all app data is accessed only through the organisers' zaic_tools, with exactly one ToolEnv per sample, and every call made on it must appear in the submission.

- Tie-breaking: if teams have the same final score, the organisers re-score their tool_calls with the F1 formula, ignoring the state_hash check. If they are still tied, the team with the lower average processing time per sample ranks higher.

## Submission

### I. Public Test Round (October 26 – November 16)

- Participating teams build their own solutions, run them on the organizers’ public test set, and submit result files (JSONL) via the Submission section on the Zalo AI Challenge portal. Teams are allowed up to 5 submissions per day, and the quota will be reset at the end of each day.

Scores and rankings will be displayed on the public leaderboard.

- On November 16, participating teams must submit their complete solutions, including training code, inference code, and data, in the form of a Docker package to the organizers via the “Solution Submission” form on the Zalo AI Challenge portal. Since the Docker file is usually quite large, teams should provide a checksum and a public Google Drive link so that the organizer can download it.

Each team is allowed up to 2 submissions. The organizer will only evaluate the last submission. Submission deadline: 23:59 (GMT+7).

### II. Private Test Round (November 20 – November 23)

- At 9:00 AM on November 20, the organizer will release the private test set. Participating teams will run their submitted solutions on this set and submit the result files (JSONL) via the Submission section on the Zalo AI Challenge portal, with a deadline of 23:59 (GMT+7) on November 23. The private leaderboard will be displayed in chronological order (based on submission time).

The organizer will evaluate the submitted solutions to verify results, review source code, and detect any cheating. The top 2 teams will be announced on December 2.
