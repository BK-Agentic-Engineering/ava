## Useful gaps and next choice

The existing taxonomy (excluded local source: `../plans/WORLD_FAILURE_DATASET_PLAN.md`; see FILE_SELECTION.json) and evidence review (excluded local source: `../research/WORLD_FAILURE_EVIDENCE_2026-11-03.md`; see FILE_SELECTION.json) support a few distinct gaps:

- **List versus detail:** intermediate identity is exposed before the critical value. Menu cases already hide item IDs behind a detail lookup; they do not hold list metadata fixed while changing a time value only inside an email body. Batch 04 addresses this narrower source-depth contrast.
- **Conditional false/no-write:** [Batch 05](../../data/synthetic/design/batch_05.yaml) addresses this gap with successful local replay (excluded local source: `BATCH05_REPLAY_HANDOFF.md`; see FILE_SELECTION.json). A/B observe the uniquely described light then turn it off (unconditional/true-condition controls). C changes only target.state.power to off and requires a successful false-condition observation, zero writes and zero asks. D removes only light_set and requires an empty log under the project's draft conditional-OOS policy. Excluded records in L1/L2 were not a dedicated whole-request false-branch contrast.
- **Scheduling boundary:** same route at schedule_time equal to current_time versus later, using verified runtime semantics. Pilot's stored-key-absence diagnostic is not that boundary experiment.
- **Recovery and trust boundaries:** existing rejected/no-op traces test the verifier, not justified recovery. Tool-content instruction conflicts and mixed-OOS handling need separate reviewed policies/challenge controls; they are outside Batch 04.

This is a designed contrast collection, not a representative usage distribution, sufficiency claim or estimate of private-test failures. No new research or external benchmark statistics are needed to justify this batch. Manual chat enrichment remains deferred.

### Vietnamese requests and structural similarity

The wording review used whole-collection phrase scans, WORLD-level contrasts and direct request/history examples. The marker counts overlap and omit synonyms. Of 826 requests, 226 contain selected guard phrases such as “giữ nguyên”, “không tạo” or “đừng”, 152 contain “nếu”, “trừ khi” or “chỉ khi”, 151 contain selected reference phrases, 36 contain selected literal-copy phrases and nine contain selected correction phrases. The latest-request scan misses many corrections in prior turns. Domain coverage alone does not diversify discourse.

- Early train families often give a full object, exact payload and trailing “không tạo/không đổi” guard. TR1_N_APPEND and TR7_C_TWO are clear controls, yet expose the desired operation or scope unusually directly. TR11 repeats “cuối cùng tôi vừa chốt” across apps. That isolates evidence selection but supplies a recurring lexical cue.
- Other constructions express the same kind of decision through different language. TR10_REM_COMPLETE names a record and its date, while TR13_REM_COMPLETE uses “cái vừa tạo sau cùng”. TR15_PLANNING_TOMORROW uses an earlier reminder as a clock and a calendar-specific action. T1 uses a spoken “à không” correction, EX4 contrasts selection with incidental mention, and TR15_PICKUP_CORRECTION uses a correction in a separate turn. B02_N_C presents a complete-sounding request with an absent source, whereas TR14_PLAN_MISSING states the missing time explicitly. H4 leaves the target choice unstated.
- Independent conversational realizations remain thin around implicit preservation, naturally incomplete requests, ellipsis across turns and authorized recovery. Written dates, quoted labels and formal prohibitions dominate many control families. The current review cannot establish dialect, acoustic or ASR robustness from these text designs.

There are 119 repeated normalized request groups covering 295 cases, with zero exact cross-split groups under NFC, casefold and punctuation-insensitive whitespace tokenization. Matched histories, fixtures, clocks and permissions often intentionally reuse requests and change gold. Close templates such as the repeated Wave 11 history phrasing can still be surface variants at the discourse level even when the app effects differ. Replacing a current value with a historical one, choosing a different tool, or moving from unconditional to guarded execution changes the decision itself. Exact uniqueness does not certify independence.

**Split finding.** B02_E_A and TR1_E_SEND both use a directly supplied recipient, subject and closely templated body with no retrieval dependency. The seven connected TRAIN_MAIL_DISPOSITION_01 cases remain held as a family, with their distinct reply/draft controls preserved. No split assignments changed. A random sample from the 17 existing ancestry components would inherit reviewed design choices. Separately authored evaluation needs a frozen claim, disjoint WORLD/template ancestry, independent fixture and language review, explicit duplicate adjudication and enough independently supported subgroups. New entities within a known mechanism can test transfer within that mechanism. Structural or cross-domain transfer needs distinct decisions. Representative usage, dialect and audio claims require separate evidence. Mail review (excluded local source: `TRAIN_WAVE_07_HANDOFF.md`; see FILE_SELECTION.json)

**Verifier finding.** TR9_NEWS_ALREADY explicitly says to keep one saved item if it already exists. Its standard executes an idempotent save, while the observed read-only path is rejected solely for authorized_actions. The state is identical. TR11_CHORE_EXPLICIT also has no state delta, but its request expressly asks for an assignment. Preserve both cases and distinguish “ensure state” from “perform action” in team review. The smallest proposed repair for TR9_NEWS_ALREADY is to accept a read-only path if a permitted actual response establishes saved membership. The pinned headlines and search only return article records, so this alternative is a manual-review item under the current interface. Keep the idempotent standard unless the team chooses a different observability policy. Do not accept an empty trace from a private fixture fact. Official call-matching equivalence remains unconfirmed. ### Organizer interface and review readiness

The existing organizer audit found history in 1,018 of 1,545 train records and 419 of 634 public records. The synthetic designs have history in 203 of 826 and use text mode. Organizer inputs include audio and consistently populated timezone, location, full profile and installed apps. Current synthetic inputs exercise a smaller subset. Some legacy synthetic turns use text for user messages, whereas executed histories use audio_text and paired tool calls/results. Native rendering still needs verification. Neither matching those organizer aggregate counts nor adding more tools would prove better model performance.

Train and public catalogs have 147 and 122 tools, with 25 common apps and split-specific capabilities. The local replay baseline uses the train package only. Train-only successes are not public coverage. The proposed harness must align visible schema filtering with private _meta.tools, start from the post-history WORLD, preserve raw responses and separate termination from semantic verdict. Standard trace replay checks state and allowed effects. Many observe-only goals still lack factual-answer validation. Organizer train label final_state is changed-app state, while submission uses tool_calls and state_hash. Local checks do not establish official match or hash agreement.
